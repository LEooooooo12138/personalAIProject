# HA 设备用途映射与对话选择规则

日期：2026-10-09。

家庭称呼应先对应到用户确认的实际负载，再选择该负载的默认控制通道。用途映射复用现有 `name`、`area_name`、`aliases` 与单实体允许清单；模型不能根据“第1路”“安装在某个房间”等信息猜测负载。

本轮记录用户确认的映射、选择规则及待核对范围。部署状态、真实页面操作和现场负载结果分别验收，本记录不代表这些验收已通过。

## 默认通道与命名

每个负载明确指定一个默认通道。“默认”来自用户确认，不能自动取第1路或目录中的第一条。书房灯已指定进门开关1为默认通道。

双控同一盏灯不代表需要同时操作两个通道。“打开书房灯”只为默认通道生成一份单实体提议，不展开为双路或批量下发。另一通道的用途关系记入本地清单；若将来需要单独选择该通道，应另行明确名称、权限和操作需求。

以下仅展示用途映射字段，`switch.study_primary` 为合成示例；完整启用配置与核验要求见[即时控制实现与验收记录](console-ha-control-results.md)。

```yaml
entity_id: switch.study_primary
name: "书房灯"
area_name: "书房"
aliases:
  - "书房的灯"
  - "书房进门开关1"
allowed_actions:
  - "turn_on"
  - "turn_off"
```

`name` 使用家庭实际称呼，`area_name` 使用已确认的负载房间，`aliases` 保存同一目标的已确认叫法和明确语言变体。例如“打开书房灯”命中名称，“把书房的灯打开”命中别名。保留完整开关名称有助于从旧目录称呼过渡。不要把裸“灯”或“开关1”当作全屋唯一用途，也不要为未知通道生成“房间灯”等推测别名。

用途未知的通道保留待确认状态。临时通道测试授权不等于负载用途核验，也不能代替用户对默认用途的确认。

## 对话选择与确认

明确实体、完整名称和配置别名的匹配优先于仅房间匹配，避免一个房间的无关实体过多而淹没已指明的目标。没有明确名称命中时，才使用房间候选帮助澄清。候选仍受20条上限约束，超限时拒绝或澄清，不截取前20条替用户决定。

真正同名的只读或未授权实体也必须保留在歧义判断中。不能因为只有一个实体可写，就推断用户说的是它。同名跨房间需要唯一的房间信息；同房间重名、同时指向多个目标或用途不明确时，先问用户。

查询与控制使用同一配置用途名称。实体仍存在于可见目录时，查询该映射应显示“书房灯”，不再在结果卡中退回“开关1”；未配置用途的实体沿用目录名称。过期目录可保留只读名称和别名，但不能因此产生可执行控制候选。

自然语言匹配只生成提议。管理员仍需核对卡片中的设备和动作，点击独立确认按钮后才执行；聊天文字“确认”不执行。查询、澄清、生成和取消提议均不发送 HA 服务动作。否定、引用、批量、定时、越权或不支持的动作仍受原有校验限制。

## 剩余核对顺序

1. 下一组核对客厅两块面板的6路用途，并确定“客厅灯”的默认通道；书房两路2按用户回复保留待确认，不反复要求猜测。
2. 按房间逐组核对剩余通道，记录实际负载、负载房间、用户称呼及确认来源；安装位置只作为线索。
3. 对同一负载的多个通道确定一个默认通道，检查跨房间重名和别名碰撞，将尚有疑义的项目留作待确认。
4. 只把已经确认并获准控制的默认通道加入允许清单，使用合成数据验证命名与歧义规则。
5. 在用户授权的现场窗口逐项验证真实页面提议、独立确认、HA 回读和实际负载观察；不自动扩展到其他设备或连续批量测试。

## 测试与验收边界

| 范围 | 应核对的行为 |
|---|---|
| 明确名称与语言变体 | “打开书房灯”“把书房的灯打开”选择同一已确认默认通道 |
| 未知用途 | 未登记的灯到开关对应关系不能因模型推断而放行 |
| 候选优先级 | 超过20个同房间无关实体时，明确名称仍保留；真正同名、多目标不被删去 |
| 歧义与上限 | 同名只读实体参与澄清；同房间重名不任选；空查询或真正候选超限不截断 |
| 查询显示 | 已配置名称一致；目录中缺失、隐藏或禁用的实体不被映射重新放行 |
| 过期目录 | 只读映射名称与别名仍在；控制候选为空 |
| 双控同灯 | 默认请求只有一个实体和一份提议，不向另一通道批量下发 |
| 执行边界 | 提议零写、确认单次发送、结果不确定不重放；核对状态只读取 |
| 真实家庭验收 | 分别记录页面操作、HA 观察时间和物理负载结果，不能用合成测试代替 |

代码回归、实际部署、浏览器操作和物理负载核验是不同证据。单次状态回读也不能代替断网恢复、设备重启或长期运行验收。
