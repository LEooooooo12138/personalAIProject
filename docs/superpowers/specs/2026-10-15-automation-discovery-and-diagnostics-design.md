# 自动化发现、审阅与运行诊断设计

> 历史文档：设计状态与验证结论仅对应文档日期；本次发布仅脱敏，不代表重新执行验收或完成部署。

日期：2026-10-15。状态：基于当前代码和只读数据的设计草案，待评审；未实施产品改动。

## 需求与设计顺序

用户确认两部分都需要：先从设备历史发现规律并生成可审阅建议，再检查已有自动化是否失效、冲突或没有执行。目标是家庭用户能知道“为什么建议这样做、确认后是否安装、后来是否仍正常”，并能在证据不足时看到明确的不确定状态。

先完成发现与证据、审阅与安装核对，再提供已安装规则的只读诊断，最后增加经过独立确认的管理动作。发现不等于授权；诊断不等于自动修复。数据来源、设备名称和用途以已确认的家庭配置为准。

对照 Phase4自动化设计、9/30 Console设计、10/9补全及即时控制设计、10/10组件库设计。后续规范已把部分首版范围收窄：当前绑定存在条件、独立确认的实现不能被描述为违反一个已经被覆盖的“任意规则编辑”旧目标。本设计明确将完整管理能力纳入下一阶段。

## 采集跨度的解释边界

公开版本省略本机采集窗口、报告数量及具体时间。保存了请求窗口不等于每个实体都具有完整历史；应分别呈现窗口覆盖、实体数据质量和分析所需的有效天数。

## 方案选择

| 方案 | 优点 | 代价 |
|---|---|---|
| A 扩展当前确定性检测和Console，推荐 | 复用现有权限、采集、版本、构建和确认链路，证据可追溯 | 需要补持久化运行记录及HA核对能力。 |
| B Console发现/解释，HA原生界面编辑管理 | 更快交付，减少复杂编辑器维护 | 用户跨系统操作，Console闭环不完整；可保留为复杂规则的出口。 |
| C 模型生成任意自动化 | 表达自由 | 增加延迟、幻觉、规则越界和验收成本，不作为当前主线。 |

选择A；复杂外部规则可只读展示并链接到HA，不复制完整HA编辑器。现有确定性检测不依赖云响应，自动化补全与云性能优化可分别实施。

## 页面与用户流程

保留“自动化检测”和“自动化”两个入口，职责明确。

**自动化检测**回答“数据够不够、发现了什么、为什么”：

1. 顶部状态显示连接、最近成功采集、最近分析、下一次计划以及观察时间。
2. 数据覆盖显示“目标14天 / 已采集窗口约6.9天”，并分别显示有效事件、缺失窗口、排除的实体及原因。不得把“无事件”自动当成“无覆盖”。
3. 主按钮“分析现有数据”；历史不足时解释门槛，并提供管理员可启动的有界历史补采。补采和分析分开显示，取消不会清空原记录。
4. 检测结果区分发现规律、数据不足、无符合规则、失败；有模式时显示证据卡片，点击进入审阅。异常/冲突是只读发现，不能自动变成执行规则。
5. 分析记录保留run_id、时间、算法版本、完成结果和建议新增/更新/已有数量。

**自动化**回答“待确认什么、已经安装什么、需要处理什么”：

- 标签“待审阅”“已安装”“需关注”，归档单独查看，不把ignored当停用。
- 建议卡片显示具体设备名、一句规则、触发/条件/动作、历史证据、缺少的绑定和风险提示。技术ID收于详情。
- 审阅按“触发 → 条件 → 动作 → 证据与差异 → 独立确认”推进；修改生成新版本，旧版本不能继续确认。
- 已安装列表显示最近核对时间、启用状态、最近有证据的触发/运行记录；无权限或数据源不支持时显示“暂无法核对”。
- 需关注卡片说明事实、证据时间、影响和可用下一步。诊断不能自动启用、停用、修复或触发规则。

## 一期：检测与证据

新增持久化 `AnalysisRun`，建议字段：`id, status, algorithm_version, requested_window, home_timezone, started_at, finished_at, coverage, result_counts, error_code`。分析状态为 `queued/running/completed/failed/cancelled`；完成结果分类为 `matched/no_pattern/insufficient_data`，和运行状态分开。持久化中断中的run，重启后标记中断并允许明确重跑，不能永远显示running。

覆盖以每实体、每窗口为基础，分别记录请求成功范围、recorder保留能力、有效观测、真实变化、不可用状态和损坏文件。完整采集但没有变化属于可观察的“无事件”；请求失败或历史不可用属于缺口。先保持当前14天/75%等检测参数，不偷偷降低门槛制造建议；窗口不足明确说明“当前算法无法给出结论”。后续调整分母或门槛需算法版本和回归证据。

有界补采默认目标最近14天，但先核对HA recorder实际保留范围和接口能力。复用Collector的批次、窗口、去重和checkpoint；补采维护独立进度，不能把实时checkpoint倒退。每批限量、可取消、断点继续、避免阻塞正常实时采集；空返回不能证明旧历史完整可用。

建议证据独立于不可变规则：`evidence_id, analysis_run_id, observed_window, eligible_days, hit_days, sample_count, excluded_count, exclusion_reasons, algorithm_version, example_refs`。示例引用指向本机事件，按权限脱敏展示。现有confidence应显示为“命中率/算法分数及分母”，不能称为真实成功概率。

复用现有[DetectedPattern.SampleSize/PeriodDays](../../../go-agent/internal/smarthome/types.go#L174)和Console Evidence DTO，修复 `generateSuggestionsInLocation → RuleSuggestion → 持久化 → DTO` 的证据传递缺口，不再造同义统计字段；同时明确各检测类型的分母含义，补齐命中日、有效日及覆盖语义。

语义相同的建议保持原规则版本；追加新证据，不覆盖已经确认的规则。当前按语义ID保留旧对象的逻辑需要拆开，避免后续观测永远不更新。无类型化证据的旧建议显示“旧记录未保存证据”，不从自由文本猜样本数。

## 二期：受限编辑和可靠安装

复用 `SuggestionIntent`、`BuildAutomation`、绑定版本链、服务端校验和现有二次确认。首批编辑只开放现有构建器可验证的触发时间、已支持目标、条件与动作；新增动作类型逐个增加明确合同，不能先开放任意YAML。

用户选房间→设备→实体，能力不支持、目录过期、重名未消歧时不给可写默认项。presence条件的“有人/无人”及负载用途由用户明确确认，不依据名称猜测。展示修改前后差异，提交时核对期望版本；编辑不会自动安装。

`InstallOperation` 单独保存 `operation_id, suggestion_version, config_key, expected_config_digest, phase, status, error_code, observed_at`；`config_key` 与 HA 实际 `automation.entity_id` 分开记录，不互相推导。操作在任何外部写入前先落盘；超时、重启或外部结果不确定进入unknown。

状态：`applying → confirmed / failed / unknown`。failed只用于能证明没有应用或明确被拒绝；unknown只读核对后再决策。配置已存在且摘要匹配只能确认配置写入，不能据此直接标confirmed；当前实现还包含[ReloadAutomations步骤](../../../go-agent/internal/smarthome/automation.go#L130)。必须另有部署版本支持的证据，确认映射正确、预期版本已被运行时加载，再完成归档和安装状态收敛。只看到旧运行实体、没有加载证据时继续unknown，显示“配置已保存，加载结果待核对”。配置不同显示外部修改；无权限、不可达或找不到映射时也保留unknown，不能直接重发。稳定config_key防新增重复，并不证明重试没有其他影响。

保留现有确认/忽略API，但“核对”应读取HA配置及运行状态，而非只刷新本地suggestions。归档失败不能显示“HA安装失败”；应单独显示配置应用结果与本地记录状态。安装成功也不等于规则已触发或设备执行成功。

对HA配置读写/reload具体合同先根据部署版本查官方接口和做隔离契约验证。不要另造通用HA代理；不要复制即时设备控制的proposal存储，自动化安装拥有独立生命周期。

## 三期：运行诊断，先只读

先覆盖本系统能够证明所有权的受管规则；用户指定的外部自动化可进入只读诊断，标记来源，不能自动接管或覆盖。每条发现记录 `diagnostic_id, rule_ref, category, severity, status, observed_at, window, evidence_refs, confidence_basis, suggested_next_action`。confidence_basis为证据类别而非模型猜测分数；结论可以是unknown。

规则归属区分 `managed/external/unverified`，不能凭名称或ID前缀认领。一次诊断快照记录 `checked_at`、查询窗口和覆盖程度，以及 `state/config/trace/activity` 各来源的 `available/unsupported/forbidden/retention_gap/unavailable` 能力状态；每项检查返回 `pass/finding/unknown` 和原因。全部unknown不能显示绿色“正常”。

| 检查 | 可以报告的结论 | 不能据此推出 |
|---|---|---|
| 规则配置/实体存在性 | 已核对不存在、目标实体失效、当前无法读取 | 一次网络失败就认定规则被删除。 |
| 当前启用状态 | 已启用/已停用，附观察时间 | 已启用就一定会按预期触发。 |
| 配置摘要与版本 | 与安装版本相符/外部修改/无法核对 | 任意外部修改都是错误，应自动覆盖。 |
| 触发或条件引用 | 实体不可用、引用失效；受支持条件可解释 | 猜测家庭占用含义或用户原意。 |
| 已有运行记录 | 某次trace明确显示触发、条件未满足、动作失败或完成 | 设备状态变化就是该自动化造成；动作调用成功就是物理负载成功。 |
| 疑似未触发 | 在明确可计算的预期窗口内没有可核对运行证据 | 无日志就断言未执行；手动/事件类没有固定预期时不得乱报警。 |
| 规则冲突 | 可静态证明的同触发/条件范围内、同目标相反动作；其余标“可能冲突” | 不同时间或互斥条件下的规则必然冲突。 |

停用和条件未满足本身可能是正常行为，不统一标为故障；只有和明确期望矛盾时才升级。不采用“24小时没运行就是失效”等家庭行为阈值，预期窗口和允许延迟来自可解释规则或用户设置。无预期合同就展示观察事实。[HA官方排障说明](https://www.home-assistant.io/docs/automation/troubleshooting/)

运行证据优先采用部署版本确实支持的HA trace/历史记录能力；先协商能力和保留范围。没有trace、无权限、历史过期或覆盖缺口时显示“无法判断”，不得伪造最近执行记录。最初只对当前构建器可解释的定时/状态规则计算预期窗口，考虑HA家庭时区、DST和前置条件；不对任意模板、脚本做确定性承诺。

当前[registry.go:27](../../../go-agent/internal/smarthome/registry.go#L27)未保留完整的自动化config_key/unique_id映射，[history_events.go:10](../../../go-agent/internal/smarthome/history_events.go#L10)状态事件也没有完整context因果链。模式检测数据不能直接当规则执行归因数据；新增小范围只读适配器并复用现有OAuth、HA client与缓存。向成员展示裁剪后的证据引用，不能暴露整份trace变量、模板或logbook。

诊断不使用“运行一次”或“模拟触发”作为健康检查，因为这可能启动真实动作。需要执行的测试必须进入单独的现场验收与确认流程。[HA官方测试说明](https://www.home-assistant.io/docs/automation/testing/)

冲突检查先限定同一可比较触发、重叠且可判定的条件、相同实际目标、相反动作；合并设备与实体的关系要依赖注册表事实，不能猜负载。循环/短时间反复切换只在有因果或明确规则图证据时升级，其他情况展示可疑关联。通知默认汇总到需关注，仅对新发现、严重程度变化或恢复去重提示，不自行开通邮件/第三方推送。

## 四期：管理动作

只对本系统受管、映射可验证且当前版本一致的自动化开放启用/停用/修改/删除。每次操作展示具体规则及影响，要求独立确认、管理员权限与会话复核；调用前再取当前事实，断连/超时进入unknown，不自动重放。

停用界面明确是否终止当前动作；根据部署版本的HA合同展示行为，不能承诺撤销已经发生的设备效果。删除需要配置备份及可审阅恢复方案，但恢复仍是新的显式操作。复杂外部规则保留HA原生编辑入口。

安装记录、诊断记录、运行记录和人工管理记录分别呈现，禁止用一个confirmed字段兼任全部事实。

## 数据和API边界

| 对象 | 职责 |
|---|---|
| AnalysisRun / Coverage | 一次分析及其数据质量，不执行设备动作。 |
| SuggestionVersion / Evidence | 规则意图及可追加证据；版本不可变。 |
| InstallOperation | 跟踪一次经确认的安装及未知结果核对。 |
| ManagedAutomation | 已证明的本地规则与HA配置/实体映射，保存期望版本。 |
| Observation / Diagnostic | 带时间和来源的外部事实、诊断发现，可过期或unknown。 |

继续复用 `/admin/collection`、`/admin/analyze`、`/suggestions` 和 bindings/confirm/ignore/sharing 的认证与业务入口。新增分析run查询、建议受限修订、受管自动化查询/只读核对/诊断以及明确管理动作；路径和DTO在实施计划阶段依据现有路由确定，不把草案当成已经存在的接口。

分析长期运行改为返回run_id并有界轮询，避免一个HTTP连接承担整个任务。共享成员仅看已授权的设备与规则投影；样本证据和冲突对手规则也要做权限过滤，不泄漏未共享房间。所有写动作保留Cookie/Origin/CSRF、身份世代、版本冲突和确认边界。

老suggestion数据按兼容规则读取，缺证据/映射显示unknown；不把历史confirmed自动转成enabled。新的持久化对象采用明确版本和原子写入；失败及迁移均有备份、回退和中断恢复测试。
